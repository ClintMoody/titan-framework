00 What Is TITAN v2.0?

v2.0 adds autonomous multi-session development on top of your existing TITAN install.

TITAN v1.x (your current install)

Human-driven. You run commands one at a time: plan, build, verify. Each session requires you to orient, pick the next task, and decide when to continue.

v2.0 does NOT change any of this. All v1.x commands work identically.

TITAN v2.0 (additive layer)

Adds autonomous looping. TITAN can run continuously across sessions — self-orienting, picking tasks, implementing features, verifying E2E, and only escalating to you when stuck.

Think: start the loop before bed, wake up to features built.

Zero Risk to Existing Install

v2.0 adds new files alongside your existing ones. No existing file behavior is changed. All v1.x commands, agents, and workflows continue to work exactly as before. The v2.0 features are opt-in — you only use them when you choose to.

Your existing workflow, now with v2.0 enhancements active behind the scenes.

What's Different Under the Hood

B
/titan:07-build — E2E Smoke Test

After all build waves complete, if a MANIFEST.json exists, a quick E2E smoke test runs to catch obvious breakage before you move to verification. Non-blocking — it warns but doesn't stop the build.

V
/titan:08-verify — E2E Verification Layer

If MANIFEST.json exists, Part 1b runs domain-specific E2E verification on features before the adversarial review. Features only move from "failing" to "passing" when E2E checks pass.

A
/titan:audit — Staleness Detection

If .titan/docs/ exists (from bootstrap), the audit now checks for stale documentation — files not updated in 10+ sessions, broken cross-references, references to deleted code.

T
All 9 Agents — Bash-First Tooling

Every agent now has a "Tooling Preference" section encouraging bash and standard CLI tools over specialized wrappers. This follows research showing models perform 3.5x better with generic tools.

New Power Tools You Can Use Anytime

# Run E2E on ALL passing features (regression test)

05 What Happens in Each Autonomous Session

The 5-step protocol that every loop iteration follows.

SESSION START | v [1] ORIENT Read PROGRESS.md (last 3 sessions) | Read LOOP-STATE.json | git log --oneline -10 v [2] VERIFY ENV Run init.sh | Run smoke test | If broken: FIX FIRST (no new work) v [3] SELECT TASK Read MANIFEST.json | Pick highest-priority "failing" feature | Check dependencies are "passing" v [4] IMPLEMENT Build the feature | Write/update tests | Verify end-to-end | Only mark "passing" after E2E passes v [5] CHECKPOINT git commit | Append to PROGRESS.md | Update LOOP-STATE.json | Ensure clean state (no half-built features) v SESSION END → NEXT SESSION

The Three Iron Rules

1
One Feature Per Session

Prevents the "build everything at once" failure mode. Each session targets exactly one feature from MANIFEST.json.

2
Fix Before Build

If the smoke test fails, the entire session becomes a fix session. Never layer new features on a broken foundation.

3
Clean State is Non-Negotiable

Every session ends with committable, test-passing code. No TODO stubs, no commented-out blocks, no failing tests.

06 Running the Loop Overnight

For true unattended operation, use the shell script directly.

The /titan:loop-start command runs within a Claude Code session. For true overnight runs where you want the loop to persist beyond any single session, use the shell script:

# From your project root (where .titan/ lives):

# Run until all features pass
./scripts/titan-loop.sh

# Run a maximum of 5 sessions
./scripts/titan-loop.sh 5

07 Understanding MANIFEST.json

The heart of the autonomous loop. Every feature, tracked as JSON.

{
  "id": "F-001",
  "category": "core",
  "description": "User can create a new project with audio file import",
  "acceptance_criteria": [
    "File picker opens on 'New Project'",
    "WAV/AIFF/FLAC files accepted",
    "Progress indicator during import",
    "Project appears in sidebar after import"
  ],
  "priority": 1,
  "status": "failing",
  "dependencies": [],
  "estimated_sessions": 1
}
MANIFEST Guard

Do NOT remove or edit feature definitions. Only the status field may be changed, and only after end-to-end verification passes. This prevents premature victory declarations and protects the feature list as source of truth.

Status Lifecycle

failing → implemented (in session) → E2E verified → passing

Features can regress back to "failing" if a regression test (via /titan:verify-e2e --all) discovers a previously-passing feature now fails.

09 Optional: Knowledge Store OPTIONAL

Semantic search across sessions and projects. $0/month, fully local.

After many sessions, flat-file grep becomes a bottleneck. The knowledge store adds semantic search so the agent can ask "how did we fix the NaN issue?" and find relevant past encounters.

Setup

# Install dependencies
brew install ollama
ollama pull nomic-embed-text     # ~270MB, local, free
pip install sqlite-vec

# Initialize the database
./scripts/knowledge-store.sh init

Usage

# Semantic search
./scripts/knowledge-store.sh search "NaN in FFT output"

# Check database status
./scripts/knowledge-store.sh status

# Re-index flat files
./scripts/knowledge-store.sh ingest

The knowledge store degrades gracefully — if Ollama isn't running, it falls back to keyword search. If the database doesn't exist, everything still works via grep.

11 Design Principles

The philosophy behind v2.0, synthesized from Anthropic, OpenAI, Vercel, and OpenClaw research.

  1. The environment IS the prompt. Documentation, file structure, git history, and enforcement rules collectively tell the agent what to do.
  2. Incremental over one-shot. One feature per session. Always.
  3. Verify like a user, not like a compiler. E2E testing catches bugs that unit tests miss.
  4. Clean state is non-negotiable. Every session ends with committable code.
  5. JSON for state, Markdown for humans. Models are less likely to corrupt JSON.
  6. Generic tools over bespoke wrappers. Bash has billions of training tokens. Use what the model knows.
  7. Mechanical enforcement over prompt engineering. Pre-commit hooks can't be sweet-talked.
  8. Escalate, don't spin. Three failures = ask a human.
  9. The repository is the single source of truth. Everything lives in the repo.
  10. Trust the model. Given the right harness, frontier models can ship features autonomously.
